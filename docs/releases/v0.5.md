# PORT v0.5 release notes

## v0.5.0

*Prepared 2026-10-14 (nothing tagged or published: v0.4.2 is the latest release).* A minor release of `@valancex/port-web`. Before 1.0 a minor version is a new range; this one only adds. Found by building one VALANCE application for the web and for a native window, which asked the Web PORT for three things its realization table could not say.

### Constant attributes

A primitive may state attributes it always has: `checkbox: { element: "input", attributes: { type: "checkbox" }, props: { ... } }`. They are written on every draw and every server render, and hydration verifies them like any attribute, so an `<input>` can be a checkbox without a prop for its `type`. A constant cannot share an attribute with a prop, cannot be an event handler (`on...`) and cannot be a URL slot (`href`, `src`, ...): constants are what the element is, never data or code. A table that does is refused with `invalid-primitives`, on the client and on the server.

### `controlledBoolean(name)`

`controlled`'s counterpart for a flag the user changes (a checkbox's `checked`): a boolean slot that is both the boolean content attribute and the same-named DOM property. It is serialized and hydrated as the attribute (present when `true`), so a ticked checkbox has an HTML form; and after every `draw`, `update` and `hydrate` the property is made equal to the rendered boolean, whatever the user did to the control since. A plain `property` has no HTML form, so a checkbox using one could not be server-rendered ticked.

### An event made by one key

An event may be realized by one key of a keyboard event: `submit: { type: "keydown", key: "Enter" }` is what a person does by pressing Enter in a field (`KeyboardEvent.key`). Any other key is not that event: at that node it does not apply, and the interaction goes on toward the root like any that does not. `key` is allowed only on `keydown` and `keyup`, non-empty, at most 32 characters.

### Compatibility

Additive. `WebPrimitive` gains an optional `attributes`, `PropRealization` gains a member (`controlled-boolean`), `EventRealization` gains an optional `key`, and the client and server entries export `controlledBoolean`. A table that does not use them is unchanged, and so is every error `code`. Code that switches over every `PropRealization` kind needs the new case. The peer range of `@valancex/mesh-runtime` is unchanged (`^0.6.0` through `^0.12.0`).

### Not in this release

The Desktop PORT (`valancex-port-desktop`) is not part of it: it stays unreleased, in the changelog's "Unreleased" section.

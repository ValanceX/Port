# PORT v0.4 release notes

## v0.4.2

*Released 2026-10-14 (`v0.4.2`).* A patch release of `@valancex/port-web`. It changes no API and no behavior.

- **The `@valancex/mesh-runtime` peer range accepts MESH 0.11 and 0.12** (`^0.6.0 || … || ^0.10.0 || ^0.11.0 || ^0.12.0`). A 0.x caret admits one minor only, so an application on MESH 0.11 or 0.12 got a peer warning. PORT only ever sees the keyed tree a runtime renders, so MESH 0.11's retirement of the `mesh-if`, `mesh-each` and `mesh-switch` elements (blocks `{#if}` and `{#each}` replace them) does not affect it: the same render trees reach `draw`, `update` and `patch`.
- **The MESH integration test uses blocks.** `integration/test/mesh-dynamic.test.ts` writes its conditional and repeated content as `{#if}` and `{#each}`; it ran against a MESH 0.11 build for this release (13 tests).
- **Compatibility.** Additive: an application on MESH 0.6 to 0.10 keeps working. The architecture test pins the range (every MESH 0.x line from 0.6, with no gap, through 0.12).

Release order: MESH 0.12.0, NEXUS 0.12.3, **PORT Web 0.4.2**, VALANCE 0.10.0.

## v0.4.1

*Released 2026-10-10 (`v0.4.1`).* A patch release of `@valancex/port-web`. A URL attribute (`href`, `src`, `action`, `formaction`, `poster`, `cite` and the other attributes a browser follows) never holds code: a `javascript:` or `vbscript:` value, or a `data:` URL in a navigating attribute, is refused as `unrealizable-value` by draw, update, hydrate, `patch` and the server's HTML, because they realize a prop by one rule. Nothing else changes. A table that really needs such a URL realizes the prop as a property (`property(name, "value")`), which is not a text slot and is the application's explicit choice.

## v0.4.0

*Released 2026-10-10 (`v0.4.0`).* A minor release of `@valancex/port-web`. Before 1.0 a minor version is a new range; this one only adds.

### `patch(patches)`: apply an update in place

MESH 0.10's `update` and `updateChanges` return the new render **and** the `render-patch-v1` operations that turn the previous tree into it. `WebPort.patch(patches)` applies them to the DOM in place: `setProp`, `removeProp` and `setText` change a kept part; `insert`, `remove` and `move` add, take away and reorder parts among their siblings by key; `replace` swaps the whole tree. A part the patches do not name is not touched, so an element a user is typing in keeps its focus and selection, and the work is proportional to the change. The patches are validated against the drawn tree first and applied all or none; a refusal is a `WebRealizationError` with a `code` (`not-drawn`, `unsupported-patch`, `unknown-key`, `patch-failed`). A key index, kept by `draw`, `update`, `hydrate` and `unmount`, lets a patch find its target without walking the tree.

### `unmount` and `Symbol.dispose`

`unmount()` is safe to call twice and before any `draw`, and leaves the PORT usable: `draw` draws again, and `update` and `patch` refuse with `not-drawn`. Where the platform has `Symbol.dispose`, the Web PORT has `[Symbol.dispose]()`, the same as `unmount()`, so `using port = createWebPort(...)` works.

### `inspect` (not part of the contract)

`WebPort.inspect` and the touched keys `patch` returns are devtools hooks. They may change or go in any release.

### Compatibility

Additive for code that **calls** the Web PORT. The `WebPort` interface itself gained members (`patch`, `inspect`, `[Symbol.dispose]`), so code that **implements** it, typically a wrapper that returns `{ draw, update, hydrate, unmount }` typed as `WebPort`, no longer typechecks until it either adds them or is typed as what it needs (VALANCE's `Target` / `HydratableTarget`). VALANCE's own test suite had about thirty such wrappers. The peer range of `@valancex/mesh-runtime` is `^0.6.0 || ^0.7.0 || ^0.8.0 || ^0.9.0 || ^0.10.0`. See the [API stability](../stability.md) page for what each surface promises.

### Not changed

`attribute`, `booleanAttribute`, `controlled`, `property`, `textProperty`, event resolution, keyed update, hydration verification, server rendering.
